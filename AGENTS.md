# AGENTS.md

Instructions for AI coding agents working on AnyDag, and a short version of
[`CONTRIBUTING.md`](CONTRIBUTING.md) for anyone in a hurry. Claude Code reads
[`CLAUDE.md`](CLAUDE.md) (the map of the code); every other agent reads this file. Each is meant to
be enough to start from, and each links to the other. **Read both before your first change**, then
the architecture file for the area you touch.

AnyDag is a local-first desktop app: an infinite canvas that draws technical diagrams from a DSL,
plus notes, tables, quizzes, tasks and attachments, all plain files in a folder (a *vault*). It is
TypeScript, React, Hono and Electron, in one repository.

## Before you write any code

1. **Work only on an accepted issue.** An issue is accepted when it carries `status: ready`. Do not
   start on one labelled `status: triage`, `status: needs-info` or `status: blocked`, and do not open
   a PR without an issue. If the task has no issue, open one from the template and stop; the
   maintainer decides whether it is ready. (PRs by the owner and by bots are exempt.)
2. **Say you are on it**: comment on the issue, and ask for `status: in-progress` if you cannot set it.
   Check that nobody else already has a branch or PR for it.
3. **Check the issue's `agent:` label** and work on it only with a model of that tier or above
   (see *Which model works on which issue* below). If the work turns out harder than the tier says,
   stop and comment asking for a higher tier; do not push on.
4. **Read the right architecture file.** [`docs/architecture/README.md`](docs/architecture/README.md)
   lists them; the table in `CLAUDE.md` says which one covers which area. Most of the code's traps are
   written down there, with the defect that found each. If the area you touch has a *Things that will
   bite* entry, read it.

## Which model works on which issue

Every `status: ready` issue carries one `agent:` label, set at triage, that says how much reasoning
the work needs. The rubric is in [`CONTRIBUTING.md`](CONTRIBUTING.md#agent-tier). A tier maps to a
model like this:

| Label | Model | Effort |
|---|---|---|
| `agent: light` | GLM 5.3 Flash (`opencode-go/glm-5.3-flash`), or Claude Haiku 5.5 | default |
| `agent: standard` | Claude Sonnet 5.5, or GLM 5.3 Flash (`opencode-go/glm-5.3-flash`), or DeepSeek V4.1 Flash (`opencode-go/deepseek-v4.1-flash`) | max for GLM and DeepSeek, default for Sonnet |
| `agent: deep` | Claude Opus 5.5 | high |

When you **open** an issue, propose a tier in it ("Suggested tier: `agent: standard`, because …");
the maintainer sets the label. An issue with no `agent:` label is not ready.

## Branches and pull requests

- `develop` is the default branch and where every PR goes. `main` holds released code only and
  changes only through a PR from `release/X.Y.Z` or `hotfix/X.Y.Z`; never target it.
- Branch from `develop`: `feat/<issue>-<slug>`, `fix/<issue>-<slug>`, `docs/<slug>`, `chore/<slug>`,
  `refactor/<slug>`, `test/<slug>`, `ci/<slug>` — for example `fix/142-note-title-focus`.
- Commits and the **PR title** are [Conventional Commits](https://www.conventionalcommits.org/):
  `feat(notes): …`, `fix(canvas): …`, `docs: …`. CI checks the title. Scopes follow the `area:` labels
  (`canvas`, `dsl`, `notes`, `tables`, `quizzes`, `tasks-calendar`, `sync`, `api`, `desktop`, `cli-mcp`,
  `assistant`, `ci`).
- The PR description says `Closes #<issue>` for the `status: ready` issue it implements. CI fails a PR
  into `develop` that does not close one.
- Keep a PR to one issue and one concern. Merges into `develop` are squash merges, so the PR title
  becomes the commit message; make it say what changed.
- Do not delete branches after merge. Do not add attribution trailers or "generated by" lines to
  commits, PR descriptions or comments.
- Every PR from someone other than the owner needs the owner's approval. Address review comments with
  new commits on the same branch; do not force-push over a review in progress.

## Before you push

Run **`npm run checks`** (Biome lint and format check, knip, typecheck, the `check:*` contracts, `docs/parity.json`, unit tests).
It is also the pre-commit hook; do not skip it with `--no-verify`, and do not push on red. Then:

- **Add or update tests** for the behaviour you changed: unit tests in `test/`, browser checks in `e2e/`.
  A bug fix includes the test that fails without it.
- **Update the docs** that describe what you changed: the matching file in `docs/architecture/`,
  `docs/dsl/` for grammar, `skills/anydag/` for anything an agent drawing on the canvas must know
  (`npm run check:skill` holds the skill to the code).
- **A new route or MCP tool is a line in `docs/parity.json`** in the same commit, and so is a new
  `anydag` command — which is added only for admin work; every other feature marks the CLI column
  `{"admin": false}`. Run `npm run parity` to redraw `docs/PARITY.md`. The checks fail otherwise.
- The browser suite runs in CI in the Playwright Docker image. To run it yourself use
  `npm run e2e:docker`. Run only the specs for the area you changed when iterating, and measure
  flakiness at no more workers than the machine has cores.
- **Screenshots are never updated casually.** The visual baselines are valid only in the Playwright
  Docker image. Update one only when a pixel change is the point of the PR, with
  `--update-snapshots=all` inside the Docker runner, and look at every changed image before you commit
  it. If a baseline fails and you did not mean to move pixels, that is a regression: fix the code.

## Never

- Never commit directly to `main` or `develop`, and never push to them.
- Never rewrite history (`push --force`, rebase of pushed commits) on a shared branch; `release/*`,
  `hotfix/*`, `nightly/*`, `develop` and `main` are shared.
- Never commit secrets: API keys, tokens, `.env` files, `server.json`, anything from a person's app
  home. `.env.example` is the only env file in the repository. If you find a secret, stop and report it
  privately (see [`SECURITY.md`](SECURITY.md)); do not put it in an issue or a PR.
- Never change the colours in `themes/*/theme.json` to make something pass or look better. A theme
  change is a design decision made by the maintainer.
- Never add a colour literal, or a length or SVG style value on the diagram surface, in `src/`. A colour
  is `var(--dag-color-…)` or `theme.color.…`; a size is `theme.metric.…`. `check:literals` and
  `check:theme` enforce it; the app chrome in `src/styles/chrome.css` is the one exemption.
- Never import browser APIs or `@/` aliases into `src/board/`, `src/dsl/`, `src/note/`, `src/quiz/` or
  `src/table/`; the server and the CLI bundle them as plain Node.
- Never write a vault's files with `fs` from the CLI or the MCP server; every read and write goes
  through a route, so the sha1 base, the 409 and the watcher apply.
- Never delete or overwrite someone's files in `boards/` or a vault when cleaning up after a test: a
  cleanup matches only the folder the test made, and does nothing if it does not know its name.
- Never call a model provider, open a network connection or send telemetry from a test that is not
  built to; the suite answers *no* to anonymous logs and mocks `/generate`.
- Never add a dependency without saying why in the PR. Prefer what is already in `package.json`.
- Never widen scope. If you find another bug, open an issue for it.

## The few rules of the codebase that matter first

These are the short form of `CLAUDE.md`; the reasons are in `docs/architecture/`.

- Layers have things they must not know (`docs/architecture/layers.md`): the format never knows
  diagrams, the grammar never knows pixels, the edit layer emits ops and never spells a statement.
- Every write to a board is a sha1-guarded patch; undo is a version of the file. A gesture paints
  while it runs and commits once.
- `layout/size.ts` never reads the DOM. A font change re-lays out everything; `data-dag-ready` means
  finished.
- Chrome and diagram share one CSS class and `data-dag-*` namespace; grep before you name something.
- A `kind` is a `switch` ending in `assertNever`, not `kind === "note" ? … : board`.
- The server is a bundle (`server/dist/`): rebuild it, and kill a server left running, before you trust
  a test of server behaviour.
- `ANYDAG_HOME` and the vault are the user's data. Opening a vault never writes to it.
